### X-12 — history list: settled design (2026-07-28)

Designed with Joshua across one thread; recorded here so implementation can start from a fresh
context. The theme of every call below is **the backend already does most of this** — X-12 is
mostly a UI slice plus three small server additions.

**1. Filter + sort.** Default the list to the server's cwd, with a show-all affordance.
`GET /conversations` already defaults to `deps.workingDir` and takes `?dir=all` (`server.ts:620`,
D-09) — **no backend change**. Sort stays `createdAt`, newest first, exactly as `list()` already
returns. Joshua's call, explicitly for simplicity: sorting by last-activity would need either a
per-settle `touch` record appended to `index.jsonl` (the newest-wins shape `title` already uses) or
per-row `stat` of the conversation file, and neither is worth it. **Accepted consequence:** a thread
resumed a week later still sorts by its birth date, so a long-running thread sinks below newer
short ones. *Papercut to fix while in here:* `list()` compares `workingDir` as an exact string and
the server stores raw `process.cwd()` (`serve-command.ts:186`) — launch once via a symlinked path
and once via the real path and you get two buckets. Normalize both sides.

**2. Resuming never duplicates the row.** Already guaranteed by construction: `store.create()` is
called **only** when no conversation was passed to `startSession` (`server.ts:223`), so a resume
appends into the same log and writes no new index row. Nothing to build — just don't break it.

**3. No `workingDir` migration.** Joshua's call: *"Generally you just need to be able to see the old
thread, not keep it. Once you finish out what it was doing you can create a new thread just fine in
the current location."* A foreign-directory row keeps its stored dir and stays filed under its
original project; you reach it via show-all. Note this is also the only *possible* answer today for
execution: the sandbox fence is server-wide and fixed at launch, so a resumed session runs under the
current server's fence regardless of the row's `workingDir`. Per-session fences would break the
one-enforcement-point rule in `CLAUDE.md` and are firmly out of scope.

**4. Delete = a reversible masking flag, never an unlink.** Joshua's call: *"we just mask them from
the index. That way if it really is an oops, I can go dumpster diving in the json file and flip the
flag back."* Append `{kind:"deleted", id, deleted:true, ts}` to `index.jsonl`; `list()` folds it out
with the same newest-wins Map it already uses for titles (`conversation-store.ts:186`). Files on
disk are untouched, so `GET /conversation/:id` still loads a masked conversation — recovery by id
works even before hand-editing anything. **Write it to the index only**, not the conversation log:
`list()` reads only the index, so there is exactly one file and one flag to flip. Make it a *flag*
(`deleted:true` → `false`) rather than a bare tombstone, so undo is an edit rather than a
line-deletion. Confirmed by a dialog **naming the thread** (X-09 titles are already in the index
rows) — *"Delete 'refactor the append log'? This can't be undone"* is a meaningful confirm;
a bare id is a reflexive one. Masking also removes the trap that hard delete carried: both
`ConversationStore` and `DebugJournal` memoize an `AppendLog` per conversation id, so an unlink
without evicting those handles would let a queued append silently recreate the file. No live-session
guard is needed (that was for the unlink race); the UI simply doesn't offer delete on a row that is
currently open.

**5. Manual rename from a history row.** New endpoint `POST /conversation/:id/title` →
`store.title(id, title, "manual")`, which already writes to both the conversation log and the index
so the name shows everywhere and survives a restart. This completes X-09's stated scope ("inline
rename in the history list *and* the session rail") — only the rail half could be built at the time.
**Trap to handle up front:** if that conversation is *also* live in a session, writing straight to
the store leaves the session's in-memory `conversation.title` stale and the rail card showing the
old name until reload. The endpoint must check the manager first — if a session holds that id, route
through the session's title path so the `title` event fires and the rail updates; otherwise write
straight to the store.

**6. A peek is read-only; the session is materialized by the first action.** Joshua's call, and the
better framing — it replaces the "Continue here" button entirely. Clicking a history row renders the
transcript from `GET /conversation/:id` in the main pane with **no `Session` object, no manager
entry, no rail card**. This is honest, not cosmetic: a resume writes nothing to disk today
(`store.create()` is skipped, `active-leaf` only moves on an actual rewind). It solves the
rail-pollution worry ("sessions getting polluted with just 'I was just peeking' entries") *by
construction* rather than with a VS Code-style italic-preview-tab that has to be promoted and
evicted — Joshua raised the italic idea and then landed on the simpler one: don't create the thing.
The composer is simply present, and typing in it is the promotion. The peek is a **view mode over
the main pane**, not a replacement for the focused session: the rail is untouched, a running turn
keeps streaming with its card showing status, and closing the peek returns you where you were (same
shape as the existing debug-journal drawer).

**7. Lazy materialization also makes a stale browser tab self-healing.** Joshua's observation:
*"if you have an old web tab which is showing a session which doesn't exist, actually using it would
recreate it."* Correct, but it needs one change — `sendChat` posts only `{sessionId, text}`
(`web/src/api.ts:289`) and `/chat` hard-404s when the manager misses (`server.ts:594`). The client
already tracks `conversationId` per slice (`App.tsx:98`), so: send both, and have `/chat` fall back
to resuming from disk when the `sessionId` misses. A few lines, in a handler whose resume path is
already immediately below. Three things this must get right:
  - **Attach, don't duplicate.** The fallback checks the manager for a session *already on that
    conversation* before resuming from disk. Two `Session` objects over independent in-memory copies
    of one tree, both appending to one log, is exactly the X-14 hazard. This makes revival
    idempotent, so two stale tabs on one thread converge instead of forking it.
  - **Pauses do not survive; the conversation does.** `/approve` and `/answer` stay keyed by
    sessionId and stay non-revivable — a pending approval belongs to an in-flight tool call in a
    process that is gone. Revival yields the conversation at its persisted leaf, not a resumed pause.
    So a stale tab's approval card is a ghost: on revival the client must re-fetch state and clear
    it, **not** post a decision into the void. Handle this deliberately; the alternative failure mode
    is a user clicking Approve and nothing happening.
  - **Which branch does the first message land on?** `/chat` with a `conversationId` resumes at the
    *persisted* `activeLeaf`. If the peek offers branch arrows, peeking at branch B and typing should
    continue B — so either the peek is view-only at the persisted leaf, or `/chat` takes an optional
    `leaf` beside `conversationId`. **Recommended: include the optional `leaf`** — branch arrows are
    the natural way to find the point you want to continue from, and it is cheaper now than as a
    retrofit. It also happens to be precisely the *start-a-session-from-(conversation, leaf)*
    primitive X-14 names as missing. Safe to build here: X-14's H-05 blocker concerns two **live**
    sessions sharing one tree, which this is not.

**8. Titles: leave space, don't build against.** Rows render the title straight from the index; the
layout must tolerate a title changing under it later. Auto-re-titling on drift is split out as
**X-17**, which carries the note that it must cover history rows and not just the rail.

**9. Pre-H-04 logs.** A conversation recorded before 2026-07-28 can fail to resume with
`Invalid signature` (the append-only log is never rewritten). The history UI must catch this and
offer to start a fresh thread rather than surfacing a raw error.

**Built 2026-07-31 as X-12a — what shipped, and the two calls made while building.**
Points 1, 2, 3, 6, 7, 8, 9 above are implemented; **points 4 (delete-masking) and 5
(rename from a row) are not** — they are the remaining **X-12b**, deliberately cut
because neither is load-bearing for *reading* an old thread, which is what Joshua
asked for. Joshua's call on placement: the list lives in the **left rail** under the
live sessions, not in a drawer — *"it combines similar multiple concepts together and
that helps make things make sense; the top kind of feels like configuration stuff."*
The drawbacks that made a rail list look unworkable (unbounded growth pushing the
live cards off screen; live and past blurring together) are answered by his own
suggestions: **two independently-scrolling sections**, both **collapsible to their
header**, split by a **draggable divider** whose position persists. Two things only a
browser could settle: the section holds a **cap, not a fixed height** (a fixed band
left a stripe of empty rail above HISTORY with one session live), and the **divider
renders only when the live list is actually capped** — a grip that cannot move
anything reads as broken. LIVE and HISTORY are kept **disjoint** (a live thread is
filtered out of history by conversation id), which is what makes closing a session
visibly move it down — the one property the drawer layout would have traded away.
The first UI preference mechanism lands here as `web/src/prefs.ts` (namespaced
`localStorage`, every read total, defaults on corrupt/absent/throwing storage);
**X-16 and X-13 add keys to it rather than growing a second path**, which is exactly
what X-16(a) asked for.

### X-12b — built 2026-08-06: the calls the row left open

Points **4** and **5** above are now implemented, plus the empty-stub third part. What the
row asked to be decided and recorded:

**(a) Undelete gets no UI, and delete is a `DELETE` route.** The stated recovery path is
hand-editing `index.jsonl`, so a "show deleted" toggle would be a surface with no caller —
the flag is written by `store.setDeleted(id, deleted = true)`, which takes the boolean, so
restoring is one call away *if* a caller ever appears. Verified end-to-end that flipping
`"deleted":true` → `false` in that file brings the row back. The route is
`DELETE /conversation/:id` rather than `POST …/deleted`: `DELETE` names what the user is
doing, and that it is implemented by masking is ours to keep — the row is gone from their
list either way, and the difference only matters at the moment they want it back.

**(b) The peeked row simply doesn't offer ✕**, which makes "what does the rail do when the
deleted row is the one being peeked" mostly moot; the handler still clears the peek if it
ever gets there (a second tab, a stale render), because leaving a deleted thread open in
the pane is the one state that reads as broken. A live thread never appears in HISTORY at
all (X-12a keeps them disjoint), so there is no live-session case to guard.

**(c) The CLI stays out of it.** No `jlcode conversation delete`. This is a browser-list
affordance for a browser-list problem, and the file is one line of JSON either way.

**The confirm is inline in the row, not `window.confirm`.** It has to name the thread, and
a native dialog takes the name *out of* the place the name is — as well as being
unscreenshottable, which would have made the peek a smaller thing than it was. The wording
carries the second clause that makes the button safe to press: *"It leaves the list, but
stays on disk."*

**The empty-stub fix is shape (i), deferred `create()`** — the honest one, per the row's own
recommendation, rather than masking-on-close which writes a row and then hides it. The audit
the row asked for holds: nothing reads the index during the live-but-silent window. The
browser filters live conversations *out* of HISTORY by conversation id, and both the peek
and `/chat`'s revival fallback read the conversation **log**, not the index. `create()` is
now issued by the first `entry` event (and by a `title` event, since a hand-rename can land
before the first message — index records fold by id, not by order, so it only has to make
the row exist). "Empty" therefore resolves to the agreed definition for free: any entry
implies a user entry above it.

**One test needed changing, and it is worth knowing why.** `test/persistence-fault.test.ts`
jams a conversation log by `chmod`-ing it right after `POST /session` — which no longer
exists at that point. The helper now creates the file empty before jamming; appends open
with `"a"`, so the only difference is that the header write fails alongside the entry, which
is the same fault under test. A test that assumed eager creation is exactly the tripwire
this change should have hit.

| D-49 | **Provider pinning is sticky per conversation, derived from the log — not configured.** OpenRouter routes each call independently, so a conversation can be served by Anthropic on turn 1 and Amazon Bedrock on turn 3. Anthropic `thinking` blocks carry a signature only the minting backend can verify, and we replay `reasoning_details` verbatim (D-14) — so a silent re-route rejects the whole history (H-02). **Mechanism:** the backend OpenRouter reports (top-level `provider`, present on every chunk) is recorded on the `AssistantEntry`; `pinnedProvider()` folds the **replayed window** — same path walk, same `replayCut` reset as `buildWireMessages` — and returns the first one found; `buildRequest` sends `provider:{order:[pin],allow_fallbacks:false}`. **Not** stored as separate conversation state and **not** a config field (Joshua's call over a per-config provider): deriving it from entries means old logs simply don't pin, forks inherit their own branch's pin, and compaction *releases* the pin for free — the summary drops `reasoning_details` (D-29), so no signature survives to protect. `allow_fallbacks:false` is deliberate: a failover would 400 on the signatures anyway, so "that provider is unavailable" beats an opaque `Invalid signature in thinking block`. **Cost:** a conversation loses OpenRouter's failover once pinned — accepted, since the alternative is a hard failure. Verified live against OpenRouter that chunks carry `provider`, that `order` accepts the reported display name verbatim (no slug mapping needed), and that an unroutable pin 404s rather than silently falling back | Joshua's call (sticky-per-conversation over a config field): it needs no maintenance, is correct across model switches, and self-corrects at a compaction boundary. | D-48 | **Learn-on-pause: settle JLCode's MCP guesses at a stop that is happening anyway (Joshua's call, P7b).** JLCode guesses conservatively about an MCP server it doesn't control — the tool **writes** (D-47b) and a slashy arg **is a path** (D-47d) — and those guesses are exactly what make it stop. So the pause carries the questions: *does `<tool>` write anything?* and *is `<field>` a file path?*, answered in the browser alongside approve/deny and persisted into the owning `mcp_settings.json` (`writeTools`/`readTools` beside `pathFields`/`notPathFields`). **It never creates a pause just to ask** — under `full-auto` with in-fence args the call runs unattended and nothing is asked, because the answer would not have changed the outcome and the user may not be at the keyboard. Three consequences: (i) the questions ride on a policy prompt or an out-of-fence escape; (ii) a **mode/policy denial that rests only on the presumed write** (Ask mode, `read-only`) becomes the write question instead of a silent wall — answering *read-only* reclassifies the tool and the call proceeds, *writes* denies it permanently, so a genuinely read-only server is usable in Ask mode without leaving it; (iii) answers are **facts about the tool, not consent** — they are kept on a deny too, and applied *before* the fence is re-evaluated, so a field the user just called prose widens nothing. `readOnlyHint` still settles write-ness with no question, unanswered stays fail-closed, and a bridged tool's `kind`/`mutates` are live so the next call sees the answer. | Joshua: "if the mode of the tool would allow the write through anyways, stopping doesn't make sense because our end action is the same either way and the user might not be at the keyboard." The corollary is the value: when JLCode *is* stopping, the user is already here, and one question settles the guess forever — both facts (writes? path?) come from the same look at the same call. Denying forever on an unverified guess was the one case where the strict default cost capability with no way to correct it | SPEC §3, §9; D-47b/d, D-19 |
| D-47 | **MCP client design — four calls (Joshua's, at the top of Phase 7).** (a) **Config = JLCode's own `mcp_settings.json`, KiloCode's shape verbatim** (`command`/`args`/`env`/`disabled`/`alwaysAllow`/`timeout`), in the config store, plus an optional per-workspace `.jlcode/mcp_settings.json` that **replaces** a global entry of the same server name; `jlcode mcp import` copies KiloCode's file (VSCodium `globalStorage/kilocode*/settings/`) over once. JLCode owns the file, so learned settings can be written back to it. (b) **Gate classification = conservative + annotations:** a discovered MCP tool is `kind:"command"`, `mutates:true` by default — Ask mode blocks it, `manual`/`auto-safe` prompt — demoted to `kind:"read"`, non-mutating only when the server sends `annotations.readOnlyHint`; the server's **`alwaysAllow`** list is honored as a per-tool pre-approval (skips the prompt under `manual`/`auto-safe`, never overrides the **mode** gate or `read-only`). (c) **stdio transport only in v1** — `command`+`args`+`env`, JSON-RPC over a spawned child; remote (`url`, streamable HTTP/SSE) lands later under the same config shape. (d) **Path fencing = learned per-server field classification.** MCP args are arbitrary JSON, so `pathArgs` (a hand-declared top-level name list) doesn't reach them: args are **flattened to jq-style dot paths** (array elements collapse to `[]`, so `edits[].path` is one field) and each server entry carries **`pathFields`** (is a filesystem path) and **`notPathFields`** (is not). A string value **containing a slash** whose field is in *neither* list **asks the user** — *is this a path?* — and the answer is **persisted into the owning `mcp_settings.json`**, so each field is asked at most once. Classified-as-path values then run the ordinary D-19 soft fence. Until a field is answered it is treated **as a path** (fail-closed). **(e) Lifecycle (Claude's call during P7a, flagged for review):** **one child per server per JLCode instance**, started before the server listens and shared by every session — cheap, and it matches how KiloCode runs them. The caveat: a server holding in-memory per-session state (file_utils remembers a `project_root`) then shares it across concurrent sessions, which is the one crack in D-36's anti-entropy invariant. Per-session children are the alternative if that bites | Joshua's calls: KiloCode configs port over verbatim (X-01) without coupling JLCode to a VSCodium install; MCP servers can't be trusted to describe their own risk, so default to the strictest class and let the server's own `alwaysAllow` (and the mode gate) relax it; stdio covers every server he runs today at a fraction of the surface; and fencing arbitrary MCP arguments can't be guessed reliably — a learned white/blacklist asks once, is exact thereafter, and never fails open | SPEC §3, §9; X-01 |

| D-46 | **Persistence failures stop the session and offer Retry; append logs hold no cached fd (closes H-01).** Two coupled fixes to `AppendLog`. **(a) Fault, don't swallow.** A failed write keeps its record at the **head** of the queue with later appends stalled behind it, then raises a fault; `flush()` rejects instead of resolving green, and the server stops discarding the one promise carrying the error. The session enters **`awaiting-persistence`**, reusing the hard-stop unwind so the running loop settles at its existing safe points, and the browser shows a blocking banner with **Retry** (plus an explicit, labelled discard). Draining past a failure was the actual corruption risk: record N+1 would persist referencing a parent that never wrote → dangling tree on load. **(b) No cached descriptor.** Each record opens/writes/fsyncs/closes under `await using` (`Symbol.asyncDispose`), so fds cannot accumulate — the EMFILE half of H-01 stops existing by construction rather than by an LRU. Measured: the extra open/close is **within run-to-run noise** of the ~140ms fsync that dominates, and trivial beside an LLM round-trip. | Joshua: "not being able to write to the hard drive should be considered something worth stopping over" — disk-full is recoverable *if* you stop (free space → Retry → intact conversation) and silently corrupting *if* you don't. On fds: Node's context-manager equivalent (`await using`) only bounds *scoped* lifetimes, so the real fix was to stop keeping handles long-lived at all — simpler than pooling, and it preserves D-37's single-queue ordering, which lives in the queue, not the handle | Joshua; ROADMAP H-01, D-37/D-13 |
| D-44 | **Compaction trigger = authoritative usage, accept one-turn overshoot (Joshua's call). No token estimator on the mainline.** Every OpenRouter response returns authoritative `prompt_tokens` + `completion_tokens`, so after each turn the *next* request's prefix is known exactly (last `prompt` + last `completion`). Compare **that ground-truth number** to the budget (`window − max(reservedOutput, buffer)`, D-27) and compact **before the next send** — i.e. react **one turn late**. The only unmeasured content is the brand-new user message + tool outputs added on the turn that crosses the line, and **we accept blowing past the limit by up to that one turn** (Joshua: "I am okay with blowing past the limit by the value of a single LLM turn"). This gives the ~20K **buffer** a precise meaning: it is exactly the headroom that absorbs that one accepted overshoot turn, not a fudge factor for a heuristic. **No tokenizer dependency, no from-scratch counting** (honors D-25). Two residuals, neither a precise accountant: **(a) cross-model compactor-fit guard** — no authoritative count exists for a summarizer never sent to, so proxy it with the working model's authoritative count (tokenizers within tens of %) plus the same one-turn slack, triggering conservatively; **(b) hard-wall fallback** — if a single turn's new content is so large it blows the whole buffer, the request hard-errors (`prompt > context_length`); handle **reactively** (catch over-window rejection → compact → retry), don't pre-empt with estimation. Refines D-27's trigger semantics | Joshua's call: pre-flight estimation existed only to predict the unmeasured delta before sending; accepting a one-turn overshoot makes ground-truth usage sufficient and deletes the estimator from the mainline. Cheaper, exact (not heuristic), and dependency-free — the rare over-window case is cheaper to catch than to guard | Joshua; SPEC §15, D-27/D-33/D-25 |
